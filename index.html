Architecture

Both directions, from
one binary.

Forward links reach a service near the server from a port on your machine — the normal ssh -L case.

Reverse links expose something on your machine through the server, even though your machine can't accept inbound connections at all. No public IP, no port-forwarding on your router.

Every link is declared once on each side — ghostport check validates internal consistency before anything starts.

server.toml
config
role = "server"
listen_control = "0.0.0.0:9000"
listen_data    = "0.0.0.0:9001"

[[peers]]
name = "laptop"
links = ["homedb", "laptop-dev"]

[[links]]
id = "homedb"      mode = forward
target = "127.0.0.1:5432"

[[links]]
id = "laptop-dev"  mode = reverse
listen = "0.0.0.0:8080"
Security

A handshake that
refuses impostors.

Noise_KK_25519_ChaChaPoly_BLAKE2s — both peers already know each other's static public key ahead of time. Unlike IK/XX, there's no "check the identity after the fact" step: a peer without the matching private key simply cannot complete the handshake.

Every key comes with a SHA-256 fingerprint — the same verification ritual as an SSH host key — something short enough to read aloud to the peer on the other end.

NAT traversal

One pinned control
connection.

Reverse tunneling needs the server to trigger a new stream on demand — but it can't dial the client behind NAT. GhostPort keeps one small, auto-reconnecting control connection open (client → server) carrying only tiny OpenStream signals.

Every actual byte-stream still gets its own fresh, fully-encrypted tunnel — always dialed by the client, accepted by the server. The client only ever needs outbound connectivity.

Management

A TUI that's actually
a console.

Four tabs: live Status with per-link throughput estimates, a full link editor with templates (SSH, Postgres, Redis, dev server…), Service control (start/stop/enable/install unit), and recent Logs.

Every edit is validated before it's ever written — the same Config::validate() the daemon itself runs.

Deployment

Hardened by default,
not by luck.

The shipped systemd unit runs sandboxed out of the box — scores 4.8 “OK” on systemd-analyze security. Multi-peer support lets one server accept several independently-pinned clients, each scoped to only its own links.

NoNewPrivileges ProtectSystem=strict ProtectHome=read-only CapabilityBoundingSet= RestrictAddressFamilies MemoryDenyWriteExecute
